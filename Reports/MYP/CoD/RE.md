1. 베를레 적분 (Verlet Integration)
  가장 대중적이면서 강력한 대안입니다. 현재 위치와 이전 위치의 차이를 이용해 속도를 추정합니다.
   * 사례: 천(Cloth) 시뮬레이션, 로프(Rope), 소생체(Soft Body) 물리
   * 특징: 속도를 명시적으로 저장하지 않아도 되며, 제약 조건(Constraints) 처리에 매우 강합니다. 입자 기반 물리 엔진(예: Hitman 시리즈의 초기 엔진)에서
     널리 쓰였습니다.
   * 장점: 계산량이 적으면서도 오일러보다 훨씬 안정적이며 에너지가 잘 보존됩니다.

  2. 룬게-쿠타 4차 (Runge-Kutta 4th Order, RK4)
  수치해석의 '표준'과 같은 정밀한 기법입니다. 한 프레임 내에서 가속도 변화를 네 번 샘플링하여 평균값을 냅니다.
   * 사례: 비행 시뮬레이션 (Microsoft Flight Simulator), 레이싱 시뮬레이션 (Assetto Corsa), 우주 궤도 시뮬레이션 (Kerbal Space Program)
   * 특징: 탄도학적 곡선을 매우 정밀하게 추적해야 할 때 필수적입니다. 공기 저항이 속도에 따라 급격히 변하는 초고속 탄환 시뮬레이션에 적합합니다.
   * 장점: 오차가 매우 적고 곡선 추적 능력이 탁월합니다. 하지만 계산량이 오일러의 약 4배입니다.

  3. 세미 임플리시트 오일러 (Semi-implicit Euler / Symplectic Euler)
  속도를 먼저 업데이트하고, 그 속도로 위치를 업데이트하는 방식입니다.
   * 사례: 대부분의 물리 엔진 (NVIDIA PhysX, Box2D, Bullet Physics)
   * 특징: 언리얼 엔진의 기본 물리 연산도 이 방식을 기반으로 합니다. 단순 오일러와 계산량은 같지만, 에너지가 무한히 발산하는 문제를 크게 억제합니다.
   * 장점: '가성비'가 가장 좋아 상용 게임 엔진의 표준으로 자리 잡았습니다.

  4. 벨로시티 베를레 (Velocity Verlet)
  위치와 속도를 동시에 높은 정밀도로 업데이트합니다.
   * 사례: 분자 동역학 시뮬레이션, 고정밀 입자 물리
   * 특징: RK4만큼 정밀하면서도 가속도 계산 횟수가 적어 효율적입니다.
   * 장점: 시간 가역성(Time-reversibility)이 있어 물리 시스템의 안정성이 매우 높습니다.

  요약 및 권장 사항

  현재 진행 중인 CoD 스타일의 탄도학 시스템에 적용한다면 다음과 같은 선택지가 있습니다:

   1. 현상 유지 (Euler): 탄환 비행 거리가 짧고 속도가 빠르다면 오차가 눈에 띄지 않으므로 퍼포먼스 면에서 가장 유리합니다.
   2. RK4 도입: 만약 1km 이상의 초장거리 저격 시스템을 구현하며, 바람의 영향이나 공기 밀도 변화를 극도로 정밀하게 시뮬레이션하고 싶다면 RK4가
      정답입니다.
   3. Velocity Verlet 도입: 탄환의 궤적이 매끄럽게 보이고 싶으면서도 RK4보다 가벼운 방식을 원할 때 좋은 절충안이 됩니다.

  전문적인 팁: 게임에서는 물리 적분법 자체보다 "서브스테핑(Sub-stepping)"이 더 중요할 때가 많습니다. 한 프레임을 더 작은 단위(예: 1/120초)로 쪼개서
  오일러 적분을 여러 번 돌리는 것이, 한 번의 정밀한 RK4보다 더 안정적인 결과를 낼 때가 많기 때문입니다.

  ---

  배틀필드(Battlefield) 시리즈와 같은 대규모 멀티플레이어 게임은 '현실적인 탄도학'과 '네트워크 성능' 사이의 타협점을 아주 정교하게 설계한 대표적인
  사례입니다. 배틀필드(프로스트바이트 엔진)에서 사용하는 방식과 전략을 엔지니어링 관점에서 분석해 드립니다.

  1. 물리 적분법: "Semi-implicit Euler + Sub-stepping"
  배틀필드에서도 의외로 RK4 같은 고비용 적분법을 쓰지 않습니다. 대신 세미 임플리시트 오일러(Semi-implicit Euler) 방식을 기반으로 하되,
  서브스테핑(Sub-stepping)을 결합하여 정확도를 높입니다.

   * 이유: 멀티플레이어 환경에서는 서버와 클라이언트 간의 결정론(Determinism)이 중요합니다. 복잡한 RK4는 부동소수점 오차나 계산량 때문에 서버 부하를
     가중시킬 수 있습니다.
   * 전략: 탄환의 속도가 빠를 때는 한 프레임을 2~4번으로 쪼개서 단순한 오일러 연산을 여러 번 수행합니다. 이렇게 하면 계산량은 적으면서도 궤적의 왜곡을
     물리적으로 허용 가능한 범위 내로 억제할 수 있습니다.

  2. 시스템 구조: "Projectile Manager (Data-Oriented)"
  배틀필드에서 가장 중요한 핵심은 "탄환은 액터(Actor)가 아니다"라는 점입니다.

   * 언리얼의 AActor 방식: SpawnActor는 메모리 할당, 컴포넌트 초기화, 리플리케이션 설정 등 오버헤드가 엄청납니다. 64명이 연발 사격을 하면 서버는 즉시
     마비됩니다.
   * 배틀필드 방식 (ECS 유사 구조):
       * 탄환은 단순히 구조체(struct) 데이터로만 존재합니다. (Position, Velocity, GravityScale, Drag, OwnerID 등)
       * Single Manager: 하나의 매니저 클래스가 거대한 배열에 담긴 수천 개의 탄환 데이터를 루프(Loop) 한 번으로 한꺼번에 업데이트합니다.
       * 이는 CPU 캐시 효율을 극대화(L1/L2 Cache Hit)하여, 수천 개의 탄환을 연산해도 CPU 점유율을 극히 낮게 유지합니다.

  3. 네트워크 최적화: "Deterministic Prediction"
  배틀필드는 모든 탄환의 위치를 실시간으로 복제(Replication)하지 않습니다.

   * 발사 이벤트 전송: 클라이언트가 총을 쏘면 서버에 "어디서, 어느 방향으로, 어떤 탄종을, 언제(Timestamp)" 쐈는지만 보냅니다.
   * 양방향 시뮬레이션: 서버와 클라이언트는 동일한 탄도학 알고리즘을 가지고 있으므로, 초기 조건만 같으면 각자 계산해도 탄환은 똑같은 궤적으로
     날아갑니다.
   * 히트 판정: 클라이언트에서 "맞았다"고 판단되면 서버에 알리고, 서버는 자신의 시뮬레이션 결과와 클라이언트의 타임스탬프를 대조하여 역전파(Lag
     Compensation)를 통해 최종 판정을 내립니다.

  4. 거리별 LOD (Level of Detail)
  탄도 물리에도 LOD를 적용합니다.

   * 근거리: 물리 연산을 생략하거나 매우 단순화(거의 직선)합니다.
   * 중/장거리: 공기 저항과 중력 가속도를 정밀하게 계산합니다.
   * 시각적 탄환(Tracer): 실제 물리 탄환과 눈에 보이는 예광탄(VFX)을 분리합니다. 예광탄은 부드러운 보간을 위해 별도의 렌더링 최적화를 거칩니다.

  배틀필드 방식을 본인의 프로젝트에 적용한다면? (Advice)

  지금 작성하신 UCOD_ProjMoveComponent_Base 방식은 "배틀필드 식 물리 모델"을 담기에는 아주 훌륭한 그릇입니다. 하지만 성능을 배틀필드 급으로 올리고
  싶다면 다음 단계를 고려해 보세요:

   1. Actor 탈피: 탄환을 AActor가 아닌 전용 FProjectileData 구조체로 관리하는 ProjectileSubsystem을 만듭니다.
   2. Scene Component 제거: 탄환에 컴포넌트를 붙이지 말고, 매니저가 DrawDebugLine이나 InstancedStaticMesh로 한꺼번에 그리게 합니다.
   3. 서브스테핑 도입: Tick 내에서 DeltaTime을 0.005초 단위로 쪼개서 ComputeAcceleration을 반복 호출하게 구현합니다.

  한 줄 요약: 배틀필드의 비결은 '어려운 수학(RK4)'이 아니라, '가벼운 수학을 엄청나게 효율적으로 처리하는 구조(Data-Oriented)'에 있습니다.
